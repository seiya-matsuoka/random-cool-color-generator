# 開発計画

本書は、実装前の計画から検証・公開・完成後の文書作成までの進め方を定義する。仕様の基準は [要件定義](01-requirements.md)、UI は [画面設計](02-screen-design.md)、実装方法は [技術設計](03-technical-design.md) に従う。

## 1. 基本方針と作業の区切り

- 学習目的の小規模なフロントエンド開発として、実際の機能と必要な品質確認を段階的に追加する。
- 本計画の合意や文書作成だけを、実装・インストール・公開の実行許可として扱わない。
- 各フェーズはユーザーから着手を依頼された範囲で進める。完了したら結果と残件を報告し、次のフェーズの実装・準備へ自動で進まない。
- 仕様・設計・作業範囲に影響する新たな判断が必要になった場合は確認する。命名の細部や通常の実装手順は既存の設計に従って判断する。
- 各フェーズの完了判定は実施した検証に基づく。未実施の検証や既知の失敗を合格として扱わない。
- 本書は進捗チェックリストとして更新しない。実装開始後の進捗と変更経緯は Issue / PR で扱う。

## 2. ドキュメントの構成と運用

### 2.1. 実装開始前

今回作成するのは次の 5 ファイルだけとする。

| ファイル                                         | 記載する内容                                           |
| ------------------------------------------------ | ------------------------------------------------------ |
| `docs/before-development/01-requirements.md`     | 企画、対象範囲、機能・非機能要件、受け入れ条件         |
| `docs/before-development/02-screen-design.md`    | 画面構成、操作、状態、通知、アクセシビリティ           |
| `docs/before-development/03-technical-design.md` | 技術構成、生成、保存、責務、テストと CI の設計         |
| `docs/before-development/04-development-plan.md` | 工程、完了条件、検証、役割分担、文書の運用             |
| `AGENTS.md`                                      | Codex が作業時に参照する順序とプロジェクト固有のルール |

- 実装開始までは計画の修正を反映できる。実装開始後は `docs/before-development/` を計画時点の記録として固定する。
- 実装中に仕様変更が必要になった場合は、ユーザーと合意し、該当 Issue / PR に理由・変更内容・検証を記録する。固定した計画文書を実装に合わせて自動更新しない。
- `AGENTS.md` は仕様の複製にせず、各文書への参照と作業ルールを記載する。変更にはユーザーの明示的な依頼を必要とする。
- ルート `README.md` は、実装・検証・公開・完成後の文書作成を終えた最後に作成する。空ファイルやテンプレートも途中では置かない。

### 2.2. 実装完了後

実際の実装・検証・公開状態を確認し、次の文書を作成する。

- `docs/after-development/01-requirements.md`
- `docs/after-development/02-screen-design.md`
- `docs/after-development/03-technical-design.md`

これらは実装前の文書を基に、最終仕様、実際の構成、確認できた動作、計画との差分を反映する。計画をそのままコピーして実装済みと扱わない。実装工程の完了済み一覧を別の設計書として複製する必要はない。

ルート `README.md` にはアプリ概要、実際に公開された URL、利用方法、ローカルでの実行・検証方法、技術構成、完成後の文書への案内を、完成状態に合わせて記載する。

## 3. ユーザーと Codex の役割

| 作業                         | ユーザー                                     | Codex                                                   |
| ---------------------------- | -------------------------------------------- | ------------------------------------------------------- |
| 重要な仕様・設計・範囲の判断 | 提案を確認し決定する                         | 具体案、影響、選択肢を整理する                          |
| 各フェーズの開始             | 着手する範囲を依頼する                       | 依頼範囲を確認して進める                                |
| ファイルの作成・実装         | 成果物を確認する                             | 許可された範囲で作成・変更する                          |
| 検証・不具合修正             | 操作感や意図との一致を確認する               | 自動検査、ブラウザ確認、範囲内の修正を行う              |
| Issue                        | 作成・編集・close を行う                     | 題名、目的、受け入れ条件、作業内容の下書きを作る        |
| branch・commit・push         | 作成、切り替え、staging、commit、push を行う | 読み取り専用の状態確認とコマンド・commit 文案を提示する |
| PR・merge                    | PR 作成、差分確認、merge、branch 削除を行う  | PR 本文、確認観点、レビューと修正を担当する             |
| GitHub 設定・公開            | Pages、branch 保護、公開開始を判断・操作する | 設定手順とワークフローを準備・検証する                  |

- Git / GitHub の状態変更を Codex に任せる場合は、その操作を個別に明示的に依頼する。
- commit の依頼を push / PR / merge の許可へ拡張しない。ブランチ操作や Issue 操作も同様とする。
- ネットワーク取得、依存追加、外部サービスへの変更などは、適用される承認ルールに従う。すでに明示的に許可された同じ範囲の操作について、不要な再確認は挟まない。

## 4. Git・GitHub の運用

- 基本の流れを 1 Issue → 1 作業 branch → 1 PR → `main` への merge とする。
- `main` を常に検証可能な状態に保ち、長期間の `develop` ブランチは設けない。
- branch はユーザーが作成する。名前は短い ASCII の `feat/<issue-number>-<topic>`、`fix/<issue-number>-<topic>`、`docs/<issue-number>-<topic>`、`chore/<issue-number>-<topic>` などとする。
- フェーズが大きい場合は、依存関係が分かる完結した Issue / PR に分ける。分割しても未着手の次フェーズには進まない。
- commit はレビュー可能な目的の単位に分け、Conventional Commits と簡潔な日本語の件名を基本とする。例: `feat: 寒色の生成処理を追加`。
- PR には目的、変更内容、検証結果、関連 Issue、必要に応じて画面画像を記載する。未実施の確認や制約も明記する。
- PR の差分確認、対象フェーズの検証、CI の成功後にユーザーが merge する。
- **マージ方式は `Create a merge commit` とし、作業 branch 上の各コミットを保持する。**
- CI の `verify` を `main` 向け PR の必須チェックに設定する。GitHub 上の保護設定はユーザーが行う。
- force push、履歴改変、変更を失う操作を通常の手順に含めない。
- `gh` CLI の導入は必須にしない。ユーザーが現在使用している Git / GitHub の操作方法で進められるようにする。

## 5. 実装フェーズ

### フェーズ 1: 環境構築と最小の品質チェック

**目的:** 後続の実装と検証を行える土台を用意する。

作業内容:

- 対象 branch、Git 状態、適用される指示、Node.js / npm の現状を確認する。
- React / TypeScript / Vite / Tailwind CSS v4 を設定する。公式テンプレートを参考に必要なファイルだけを追加し、既存の計画文書と設定を保持する。非空ディレクトリに対する強制的な上書きを行わない。
- ESLint / Prettier / TypeScript と Vitest の設定、基本 scripts を用意する。
- Vite の `base` を `/random-cool-color-generator/` に設定する。
- 生成物の ignore と、計画文書・`AGENTS.md` の整形対象外設定を用意する。
- format check、lint、type check、アプリ build を実行する最小の `verify` ジョブを追加する。デプロイは含めない。
- ルート `README.md` が生成されるテンプレートの自動展開を避け、途中でも作成しない。不要なサンプルを追加しない。

完了条件:

- ローカルの開発サーバーで React の画面を確認でき、対象サブパスで本番 build / preview を確認できる。
- format check、lint、type check、build に成功する。
- Vitest の設定を用意し、まだ実機能のテストがないことを明示する。この段階では単体テストを CI の必須実行項目に含めない。
- ユーザーの push / PR 後、最小の CI が成功する。外部側の実行を確認するまではローカル確認と区別して報告する。

### フェーズ 2: 生成と記録操作のロジック

**目的:** UI に依存しない中核処理を確定する。

作業内容:

- 記録の型、シード、SHA-256、HSL / RGB / HEX 変換、再試行を実装する。
- 履歴 20 件の追加・切り詰め、お気に入り 20 色の登録・重複判定・解除を実装する。
- 既知値や境界条件など、結果が明確なロジックでは、テストを先に書いてから実装する方法を一部で試す。
- Vitest と V8 coverage を実際の品質チェックへ追加する。

完了条件:

- 技術設計の既知値、色域、再試行上限と失敗、履歴上限、お気に入りの重複・上限・独立性を単体テストで確認できる。
- `check` が format check、lint、type check、単体テストと coverage を実行する。
- 単体テストとアプリ build を含む CI が成功する。

### フェーズ 3: UI コンポーネントと Storybook

**目的:** 色・情報・一覧・通知・ダイアログの状態を独立して確認できるようにする。

作業内容:

- 色表示、コード表示、一覧、通知、確認ダイアログを props とコールバックで実装する。
- 画面設計に従い、英語 UI、キーボード操作、レスポンシブ表示を用意する。
- Storybook を導入し、初期化前から telemetry を無効にする。
- CSF3 で固定状態の Story を用意し、Docs / Controls / Actions を使用する。
- `build-storybook` をローカルと CI の検査へ追加する。

完了条件:

- 空、通常、上限、処理中、異常、確認ダイアログを実際の保存データなしで確認できる。
- デスクトップ・モバイル幅の配置と、基本のフォーカス・ダイアログ操作を確認できる。
- アプリと Storybook の build、追加済みの各検査に成功する。
- Storybook の外部公開や実保存処理への接続を行っていない。

### フェーズ 4: アプリとブラウザ保存の統合

**目的:** 生成から履歴・お気に入りの利用までを 1 ページで完成させる。

作業内容:

- 起動時の読み込み、初回 1 回の生成、多重実行の防止、現在色の状態を統合する。
- 保存データの検証、履歴・お気に入りの読み書き、上限と重複の通知を実装する。
- コピー、詳細、一覧の選択、確認付き削除を接続する。
- 保存不可、破損保護、確認付きリセット、タブ間の一覧更新を実装する。
- 保存アダプターと検証処理の単体テストを追加する。

完了条件:

- 初回生成、再生成、コピー、履歴・お気に入りの保存と再表示をブラウザで確認できる。
- Strict Mode で初回生成・履歴追加が重複せず、再読み込み後も保存済みの記録を利用できる。
- 履歴削除がお気に入りへ影響せず、現在色も維持される。
- 保存失敗時のタブ内履歴と、お気に入りの変更取り消し、異常データの保護を確認できる。
- 他アプリの保存キーを変更せず、タブ間更新で表示色を変更しない。
- 単体テスト、静的検査、各 build に成功する。

### フェーズ 5: E2E・アクセシビリティ・品質チェックの完成

**目的:** 主要な利用フローと異常時の扱いを本番ビルドで検証する。

作業内容:

- Playwright を導入し、Chromium のデスクトップ幅・モバイル幅を設定する。
- 初回と再生成、履歴の再読み込み・再表示、お気に入りの保存・独立性、上限・重複・確認操作、保存失敗を主なシナリオとして用意する。
- タブ間更新と、対象キーだけのリセットを代表ケースで確認する。
- axe による代表状態の検査と、キーボード・見た目・コピーの手動確認を実施する。
- コードとブラウザの通信を確認し、生成記録の外部送信、URL への付加、実行時の外部 CDN の参照がないことを確認する。
- 失敗時の再現テストを作り、修正後に同じテストで改善を確認する方法を試す。
- `verify` を技術設計の完成時の構成にし、CI artifact にレポートを残す。

完了条件:

- 本番 build を使用した `npm run verify` に成功する。
- CI も同じ構成で成功する。モバイル幅と実機確認、axe と手動確認の結果を区別する。
- 公開前に対処すべき既知の不具合と未確認事項が整理され、必要な修正を完了している。
- 自動テストだけでは分からない操作感とレイアウトをユーザーが確認できる状態になっている。

### フェーズ 6: GitHub Pages への公開

**目的:** 検証済みの配信物を公開し、実際の URL で動作を確認する。

作業内容:

- フェーズ 5 の品質確認を終えてから、同じワークフローの検証成功 artifact を使用する公開ジョブを追加する。
- Pages の設定手順、必要な権限、公開開始後の `main` 更新による再公開をユーザーに説明する。
- ユーザーが Pages を GitHub Actions source に設定し、公開ワークフローの PR を確認・merge する。
- 公開後に URL、アセットのサブパス、生成、保存、再表示、コピーの代表操作を確認する。

完了条件:

- 品質チェックに成功したものと同じ `dist` が公開される。
- 公開 URL が HTTPS で開け、サブパスのアセット読み込みエラーがない。
- 実際に確認した公開環境の結果と、未確認のブラウザ範囲を記録する。
- 既存の利用者データを無断で削除して確認しない。必要なテストデータの範囲で操作する。

### フェーズ 7: 完成後の文書と README

**目的:** 実装・検証・公開の実際の結果を、利用と振り返りに使える形で残す。

作業内容:

- 実装、設定、テスト、公開状態、Issue / PR の合意事項を確認する。
- `docs/after-development/` の 3 文書を完成状態に合わせて作成する。
- 最後にルート `README.md` を作成する。
- 実在する文書へのリンク、公開 URL、記載コマンドと実装の一致を確認する。

完了条件:

- 計画時点と完成時点の文書を区別でき、完成時点の文書から実際の仕様・構成を理解できる。
- README の実行手順と検証手順が実際の scripts と一致し、実行・公開を確認していない内容を実績として書いていない。
- 固定した `docs/before-development/` と、ユーザーが依頼していない `AGENTS.md` を変更していない。
